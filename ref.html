Начало

Введение

Oktopus — это форвард-прокси для централизованного контроля доступа в интернет. Он перехватывает HTTP/HTTPS-трафик, проверяет учётные данные пользователя и применяет правила ACL до установки соединения с целевым хостом.

Что это даёт

  • Контроль на уровне домена — SNI-фильтрация работает без расшифровки TLS.
  • Гибкая авторизация — LDAP/AD, статические учётки или их комбинация.
  • ACL как данные — правила хранятся в PostgreSQL и пересобираются на лету, без перезапуска.
  • Полный аудит — каждое решение ALLOW/DENY фиксируется с учёткой, источником и задержкой.
  • Опциональный MITM — собственный CA для инспекции содержимого там, где это нужно.

Режимы работы

РежимОписаниеРасшифровка
tunnelПрозрачный CONNECT-туннель. Проверяется только SNI/IP назначения.нет
mitmПрокси подменяет сертификат своим CA и видит полный URL.да
rejectВсе соединения отклоняются, кроме явно разрешённых правилами.—
Совет

Начните с режима tunnel — он покрывает 90% задач фильтрации и не требует распространять корневой сертификат на клиентские машины.

Путь запроса

Упрощённо обработка одного соединения выглядит так:

поток обработки
client
  │  CONNECT github.com:443
  ▼
[ listener ]  :8080
  │
  ├─▶ [ auth ]      LDAP / static / cache
  │        └── 407 Proxy Authentication Required
  │
  ├─▶ [ acl engine ]  правила из PostgreSQL (in-memory snapshot)
  │        └── DENY → 403 Forbidden + запись в журнал
  │
  ├─▶ [ dialer ]    установка соединения с upstream
  │
  └─▶ [ access_log ]  запись решения

Требования

  • Linux x86_64 или arm64, ядро 4.19+
  • PostgreSQL 14+ (хранение правил и журнала)
  • 2 vCPU / 2 GB RAM на каждые ~500 одновременных соединений

Начало

Быстрый старт

Разворачиваем прокси вместе с базой данных через Docker Compose за пару минут.

1. docker-compose.yml

docker-compose.yml
services:
  oktopus:
    image: ghcr.io/oktopus/proxy:0.4.2
    restart: unless-stopped
    ports:
      - "8080:8080"   # прокси
      - "9100:9100"   # метрики
    volumes:
      - ./config.yaml:/etc/oktopus/config.yaml:ro
      - ./certs:/certs:ro
    environment:
      OKTOPUS_LDAP_PASSWORD: ${LDAP_PASSWORD}
    depends_on:
      - postgres

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: oktopus
      POSTGRES_USER: oktopus
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

2. Минимальный config.yaml

config.yaml
listen: ":8080"
connect_mode: tunnel
log_level: info

auth:
  enabled: false

storage:
  dsn: "postgres://oktopus:secret@postgres:5432/oktopus?sslmode=disable"

access_log:
  enabled: true
  retention: 720h

3. Запуск

shell
# поднимаем окружение
docker compose up -d

# смотрим логи
docker compose logs -f oktopus

# ждём строку
level=info msg="proxy listening" addr=:8080 mode=tunnel

4. Проверка

shell
curl -x http://localhost:8080 https://example.com -I

# HTTP/2 200
# x-oktopus-rule: 50
# x-oktopus-user: -
Заголовки отладки

Прокси добавляет в ответ x-oktopus-rule — номер сработавшего правила, и x-oktopus-user — логин. Удобно для диагностики ACL.

Начало

Архитектура

Oktopus — это один бинарник, внутри которого несколько независимых подсистем, связанных через in-memory снапшоты.

Компоненты

КомпонентОтветственность
listenerПриём CONNECT и обычных HTTP-запросов, лимиты соединений, таймауты.
authПроверка логина/пароля, кеш сессий, бэкенды LDAP и static.
acl engineДержит снапшот правил, сопоставляет запрос, возвращает ALLOW/DENY и номер правила.
dialerУстановка соединения с upstream, пул, keep-alive, DNS-кеш.
mitmГенерация сертификатов на лету, расшифровка трафика (в режиме mitm).
storagePostgreSQL: правила, пользователи, журнал доступа.
metricsPrometheus-эндпоинт и health-check.

Снапшот правил

ACL-движок не ходит в базу на каждый запрос. Раз в acl_reload_interval (по умолчанию 15 секунд) он забирает актуальный набор правил и атомарно подменяет снапшот. Все запросы в этот момент обслуживаются старой версией — разрыва нет.

жизненный цикл снапшота
t+0s    storage SELECT * FROM proxy_acl ORDER BY sort_order
t+0s    validation: дубликаты, пустые паттерны, битые regex
t+0s    atomic.Pointer.Store(newSnapshot)   ← без блокировок
t+0s    старый снапшот уходит в GC

ошибка валидации → снапшот НЕ подменяется,
                   инкремент acl_reload_failed_total,
                   лог уровня error

Масштабирование

  • Сервис без состояния — можно ставить несколько инстансов за L4-балансировщик.
  • Единственная общая точка — PostgreSQL; он же может быть репликой для чтения.
  • Сессионный кеш аутентификации локальный, поэтому балансировка должна быть sticky по IP либо TTL кеша небольшим.

Порты

ПортПротоколНазначение
8080TCPПрокси (HTTP + CONNECT)
9100HTTPМетрики и health-check

Настройка

Конфигурация

Единый YAML-файл. Любое значение можно переопределить переменной окружения с префиксом OKTOPUS_.

Полный пример

/etc/oktopus/config.yaml
listen: ":8080"
connect_mode: tunnel          # tunnel | mitm | reject
log_level: info               # debug | info | warn | error

tls:
  ca_cert: /certs/ca.crt
  ca_key:  /certs/ca.key
  mitm_hosts:
    - "*.company.ru"

auth:
  enabled: true
  realm: "Oktopus Proxy"
  backend: ldap               # ldap | static
  cache_ttl: 60s
  fail_open: false            # что делать, если LDAP недоступен
  ldap:
    url: ldaps://dc.company.ru:636
    bind_dn: cn=svc-proxy,ou=svc,dc=company,dc=ru
    bind_password: ${OKTOPUS_LDAP_PASSWORD}
    user_base_dn: ou=users,dc=company,dc=ru
    user_filter: "(sAMAccountName=%s)"
    group_base_dn: ou=groups,dc=company,dc=ru
    tls_skip_verify: false
  static:
    users:
      - login: i.petrov
        password_hash: "$2a$10$Qm..."

storage:
  dsn: "postgres://oktopus:secret@postgres:5432/oktopus?sslmode=disable"
  acl_reload_interval: 15s
  max_open_conns: 10

access_log:
  enabled: true
  retention: 720h              # 30 дней
  batch_size: 500

metrics:
  listen: ":9100"
  path: /metrics

limits:
  max_conns: 4096
  dial_timeout: 10s
  idle_timeout: 90s

Справочник параметров

ПараметрТипПо умолчаниюОписание
listenstring:8080Адрес и порт прослушивания.
connect_modeenumtunnelРежим обработки HTTPS.
log_levelenuminfoУровень логирования самого сервиса.
auth.enabledbooltrueТребовать ли авторизацию.
auth.cache_ttlduration60sВремя жизни успешной сессии в кеше.
auth.fail_openboolfalseПропускать ли трафик при недоступности LDAP.
storage.acl_reload_intervalduration15sПериод пересборки ACL.
access_log.retentionduration720hСрок хранения записей журнала.
limits.max_connsint4096Максимум одновременных соединений.
limits.dial_timeoutduration10sТаймаут установки соединения с upstream.
Важно

Параметр auth.fail_open: true открывает доступ всем при недоступности каталога. Используйте только в аварийном сценарии и обязательно с алертом на метрику oktopus_auth_backend_errors_total.

Проверка конфигурации

shell
oktopus config validate --config /etc/oktopus/config.yaml

# ✓ schema ok
# ✓ storage: connected (postgres 16.2)
# ✓ ldap: bind ok (dc.company.ru)
# ✓ tls: ca.crt loaded, expires 2027-04-11

Настройка

Аутентификация

Oktopus поддерживает базовую HTTP-аутентификацию через Proxy-Authorization с проверкой по LDAP/AD или по локальному списку.

LDAP / Active Directory

Сервис выполняет bind под служебной учётной записью, ищет пользователя по фильтру, затем повторно биндится под найденным DN с введённым паролем. Такой подход работает и с AD, и с OpenLDAP.

config.yaml — секция auth
auth:
  enabled: true
  realm: "Oktopus Proxy"
  backend: ldap
  cache_ttl: 60s
  ldap:
    url: ldaps://dc.company.ru:636
    bind_dn: cn=svc-proxy,ou=svc,dc=company,dc=ru
    bind_password: ${OKTOPUS_LDAP_PASSWORD}
    user_base_dn: ou=users,dc=company,dc=ru
    user_filter: "(sAMAccountName=%s)"
    group_base_dn: ou=groups,dc=company,dc=ru
    group_filter: "(member=%s)"

Плейсхолдеры в фильтрах

ПлейсхолдерПодстановка
%sЭкранированный логин пользователя
%dDN пользователя (только в group_filter)

Статические учётные записи

Используются для сервисных аккаунтов и аварийного доступа. Пароли хранятся в виде bcrypt-хешей.

создание хеша и запись
# генерируем хеш
oktopus user hash
# Password: ********
# $2a$10$QmXk9r2fT1sVb...

# либо сразу добавляем в базу
oktopus user add --login ci-runner --role service
config.yaml — static backend
auth:
  backend: static
  static:
    users:
      - login: ci-runner
        password_hash: "$2a$10$QmXk9r2fT1sVb..."
      - login: monitoring
        password_hash: "$2a$10$8LpQ..."

Кеш сессий

Успешная проверка кладётся в локальный LRU-кеш на cache_ttl. Ключ — пара login + hash(password), поэтому смена пароля в каталоге не инвалидирует кеш мгновенно. Уменьшите TTL, если это критично.

Ответы прокси

КодПричинаЗаголовки
407Нет или неверные учётные данныеProxy-Authenticate: Basic realm="…"
403Аутентификация пройдена, ACL запретилx-oktopus-rule
503Бэкенд аутентификации недоступен и fail_open=falseRetry-After
Совет

Для групповых правил ACL включите group_base_dn — тогда в правилах можно ссылаться на группы каталога, а не перечислять логины.

Настройка

Правила ACL

Правила хранятся в таблице proxy_acl и применяются сверху вниз по возрастанию sort_order. Срабатывает первое совпавшее.

Поля правила

ПолеДопустимые значенияОписание
sort_orderintПриоритет. Меньше — раньше.
scopeALL · GROUP · USERНа кого распространяется правило.
scope_valuestringИмя группы или логин (для ALL — пусто).
typeSNI · PATH · IP · ALLЧто именно сопоставляется.
patternglob или CIDRШаблон сопоставления.
actionALLOW · DENYРешение при совпадении.
enabledboolВыключенные правила игнорируются при сборке.

Типы сопоставления

  • SNI — имя хоста из TLS ClientHello или заголовка Host. Работает в режиме tunnel.
  • PATH — путь запроса. Требует режима mitm, иначе путь недоступен.
  • IP — адрес назначения, поддерживает CIDR-нотацию.
  • ALL — совпадает с любым запросом. Обычно используется для финального DENY.

Порядок вычисления

алгоритм
для правила в снапшоте (по возрастанию sort_order):
    если правило выключено          → пропустить
    если scope не подходит юзеру    → пропустить
    если тип не совпал с запросом   → пропустить
    если паттерн не совпал          → пропустить
    ────────────────────────────────────────────
    вернуть action правила          ← первое совпадение

если ничего не совпало              → DENY (default deny)
Default deny

В конце списка всегда действует неявный запрет. Поэтому правило sort_order: 10, ALL, ALL, *, DENY из примеров ниже — избыточно, но полезно как явная документация политики.

Пример набора правил

#ScopeTypePatternAction
10ALLALL*DENY
20ALLSNIgithub.comALLOW
30GROUP devPATH*.company.ru/admin/*DENY
40GROUP devSNIregistry.npmjs.orgALLOW
50ALLSNI*.company.ruALLOW

Добавление через SQL

SQL
INSERT INTO proxy_acl
  (sort_order, scope, scope_value, type, pattern, action, enabled)
VALUES
  (60, 'GROUP', 'dev', 'SNI', 'pypi.org', 'ALLOW', true);

Изменения подхватятся автоматически в течение acl_reload_interval. Ускорить можно вызовом API:

shell
curl -X POST http://localhost:9100/api/v1/acl/reload \
     -H "Authorization: Bearer $TOKEN"

# {"reloaded":true,"rules":19,"duration_ms":3}

Отладка

Проверить, какое правило сработает для конкретного запроса, можно без реального подключения:

shell
oktopus acl test --user i.petrov --host github.com --port 443

# user:    i.petrov
# groups:  dev, everyone
# host:    github.com
# ─────────────────────────────
# rule #20 (ALL / SNI / github.com) → ALLOW

Настройка

Журналирование

Каждое решение прокси попадает в таблицу proxy_access_log. Записи пишутся батчами, старые удаляются фоновым процессом по retention-политике.

Схема записи

КолонкаТипОписание
tstimestamptzМомент решения, с точностью до микросекунд.
logintextЛогин пользователя или NULL для анонимных запросов.
src_ipinetАдрес клиента.
dst_hosttextХост назначения (SNI или Host).
dst_portintПорт назначения.
methodtextHTTP-метод (в режиме mitm).
urltextПолный URL (в режиме mitm).
actionenumALLOW или DENY.
rule_idintНомер сработавшего правила.
duration_msintВремя принятия решения.

Retention

Фоновая задача раз в час удаляет записи старше access_log.retention. Удаление идёт порциями по 10 000 строк, чтобы не держать долгие блокировки.

SQL — ручная чистка
DELETE FROM proxy_access_log
WHERE ts < now() - interval '30 days';
Совет

Для больших объёмов переведите таблицу в партиционирование по ts (RANGE, посуточно). Тогда retention сводится к DROP PARTITION и работает мгновенно.

Полезные запросы

SQL
-- топ заблокированных хостов за сутки
SELECT dst_host, count(*) AS hits
FROM proxy_access_log
WHERE action = 'DENY' AND ts > now() - interval '1 day'
GROUP BY dst_host
ORDER BY hits DESC
LIMIT 20;

-- активность пользователя
SELECT login, action, count(*)
FROM proxy_access_log
WHERE ts > now() - interval '7 days'
GROUP BY login, action;

Экспорт

shell
oktopus log export \
  --from "2025-01-01" \
  --to   "2025-02-01" \
  --format csv \
  --out  /tmp/access.csv

Примеры

shell

  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"login":"i.petrov","host":"github.com","port":443}'

#   "action": "ALLOW",
#   "rule_id": 20,

    "sort_order": 60,
    "scope": "GROUP",
    "scope_value": "dev",
    "type": "SNI",

Команды

КомандаОписание

shell

  --config /etc/oktopus/config.yaml \

shell

  --out /certs \

Регулярно выгружайте ACL в репозиторий — так изменения правил проходят через code review, а восстановление после сбоя занимает одну команду.

Справочник

Переменные окружения

Любой параметр конфигурации можно задать переменной с префиксом OKTOPUS_. Вложенность разделяется подчёркиванием, приоритет выше, чем у YAML.

Правила маппинга

соответствие
auth.cache_ttl            →  OKTOPUS_AUTH_CACHE_TTL
storage.acl_reload_interval →  OKTOPUS_STORAGE_ACL_RELOAD_INTERVAL
limits.max_conns          →  OKTOPUS_LIMITS_MAX_CONNS
listen                    →  OKTOPUS_LISTEN

Секреты

Значения в фигурных скобках в YAML подставляются из окружения на этапе загрузки конфига:

config.yaml
auth:
  ldap:
    bind_password: ${OKTOPUS_LDAP_PASSWORD}

storage:
  dsn: "postgres://oktopus:${OKTOPUS_DB_PASSWORD}@postgres:5432/oktopus"
Важно

Если переменная не задана, сервис завершится с ошибкой на старте — молчаливой подстановки пустой строки нет. Это защищает от случайного запуска без пароля.

Часто используемые

ПеременнаяОписание
OKTOPUS_CONFIGПуть к файлу конфигурации.

FAQ

Частые вопросы и типовые проблемы при эксплуатации.

Клиент постоянно получает 407

Скорее всего, неверный бэкенд аутентификации или пользователь не найден по фильтру. Проверьте цепочку вручную:

shell
oktopus config validate --config /etc/oktopus/config.yaml

# смотрим debug-лог только по auth
# level=debug msg="ldap search" base="ou=users,..." filter="(sAMAccountName=i.petrov)"
# level=debug msg="ldap bind failed" dn="..." err="invalid credentials"

Правило по PATH не срабатывает

Путь доступен только в режиме mitm. В режиме tunnel прокси видит исключительно SNI, поэтому правила типа PATH просто не совпадут. Убедитесь также, что хост попадает в tls.mitm_hosts.

Браузер ругается на сертификат

Корневой сертификат ca.crt не установлен в доверенные на клиенте. Для домена в Windows это делается через групповую политику, для Linux — копированием в /usr/local/share/ca-certificates/ и вызовом update-ca-certificates.

Высокая задержка на первом запросе

Первый запрос нового пользователя всегда идёт в LDAP — это может занимать 50–200 мс. Дальнейшие запросы обслуживаются из кеша. Если задержка стабильно высокая, увеличьте auth.cache_ttl и проверьте сетевую доступность контроллера домена.

Правила не применяются

  1. Проверьте, что правило включено (enabled = true).
  2. Убедитесь, что sort_order не перекрыт более приоритетным правилом.
  3. Посмотрите метрику oktopus_acl_reload_failed_total — если она растёт, снапшот не обновляется из-за ошибки валидации.
  4. Вызовите POST /api/v1/acl/reload вручную и проверьте ответ.

Куда сообщать о проблемах

Баг-репорты и вопросы — в issues репозитория. Приложите вывод oktopus version, фрагмент конфига без секретов и релевантные строки лога.
