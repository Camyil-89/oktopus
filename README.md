# Oktopus

**Документация:** [русский](https://camyil-89.github.io/oktopus/ru/index.html) · [English](https://camyil-89.github.io/oktopus/en/index.html)

Oktopus — это прокси для контроля исходящего интернет-трафика. Правила доступа в стиле Squid и веб-панель, где видно, кого куда пустили, кого нет и почему.

Работает в двух режимах — Tunnel и MITM. В MITM умеет не только фильтровать по ACL, но и проверять исходящие запросы через Lua-инспекцию. Есть LDAP, журнал, отчёты и конструктор виджетов для анализа access log.

## Возможности

- **Контроль доступа** — ACL в стиле Squid: источник, назначение, домены/SNI, порты, URL, LDAP-группы, именованные списки, порядок `http_access`, задержки, проверка TLS к origin.
- **Режимы прокси** — Tunnel без расшифровки HTTPS и MITM с корневым CA на клиентах. В MITM также plain HTTP и WebSocket.
- **Инспекция запросов** — после `allow` по ACL в MITM включается цепочка Lua-правил: заголовки, тело, действия `allow`/`deny`.
- **Аутентификация** — локальные учётки или LDAP. ACL могут опираться на группы каталога.
- **Веб-панель** — запуск/остановка прокси, редактор ACL и инспекции, API-пользователи, access log, отчёты, инспектор «почему сработало правило».
- **Журнал и отчёты** — решения `allow`/`deny` с контекстом: хост, пользователь, правило, результат инспекции.
- **Расширенный анализ журнала доступа** — конструктор виджетов: временные ряды, столбчатые диаграммы, таблицы, статистика. Можно строить свои отчёты по полям журнала и данным инспекции (`inspect_log.*`).
- **Проверка политики** — интеграционные тесты в CI и API `evaluate`: вердикт `allow`/`deny` по полям запроса без прогона реального трафика.

## Производительность

Замеры на localhost: генератор нагрузки и прокси на одной машине, CPU 6 ядер ~4.3 GHz, в политике ~1.5 млн проверок SNI и включена MITM-инспекция.  

| Показатель | Значение |
|---|---|
| Пик RPS, сценарий `allow` | до ~14 000 запросов/с |
| Пик RPS, сценарий `deny` | до ~45 000 запросов/с |
| Среднее время ACL + inspect на запрос | < 1 ms |
| Потребление RAM процессом прокси | ~600 MB |

## Подробнее

### Контроль доступа
Правила описываются в привычном для Squid стиле: IP-источник, адрес назначения, домен или SNI, порт, URL-шаблон, группы LDAP. Поддерживаются именованные списки, порядок `http_access`, искусственные задержки и проверка TLS-сертификата origin-сервера.

### Режимы прокси
- **Tunnel** — обычный CONNECT-туннель без расшифровки HTTPS. Прокси видит только факт соединения.
- **MITM** — расшифровка HTTPS с корневым CA на клиентах. Доступны инспекция, plain HTTP и WebSocket.

### Инспекция исходящих запросов
Если ACL разрешил соединение, в MITM вступает цепочка Lua-правил. Она анализирует заголовки и тело запроса и может вернуть `allow` или `deny`. Это позволяет, например, блокировать загрузку файлов определённых типов или проверять параметры POST-запросов.

### Аутентификация
Клиенты могут входить в прокси через локальные учётные записи или LDAP. ACL могут ссылаться на группы каталога — удобно для корпоративной инфраструктуры.

### Панель управления
Веб-кабинет — единая точка для управления: запуск и остановка прокси, редактирование ACL и инспекции, API-пользователи, журнал access log, отчёты и инспектор правил.

### Журнал и отчёты
Все решения `allow`/`deny` сохраняются с контекстом: хост, пользователь, сработавшее правило, результат инспекции. Это основа для расследований и отчётности.

### Расширенный анализ журнала доступа
Помимо стандартного просмотра журнала есть конструктор виджетов. Администратор может собирать собственные панели:

- **Временные ряды** — динамика запросов по часам/дням с разбивкой по `allow`/`deny`.
- **Столбчатые диаграммы** — топы назначений, типов контента, пользователей и других полей.
- **Статистика** — общее количество записей, доля отказов и т.п.
- **Таблицы** — группировка по нескольким колонкам с поиском и сортировкой.

Доступны поля журнала (`destination_address`, `source_address`, `user`, `action` и др.) и данные инспекции (`inspect_log.upload_filenames`, `inspect_log.upload_content_type`, `inspect_log.upload_method` и т.д.). Можно строить отчёты, для которых раньше пришлось бы выгружать данные во внешние инструменты.

### Проверка политики
Правила ACL и сценарии обхода проверяются в CI интеграционными тестами. Через API `evaluate` можно получить `allow`/`deny` по полям запроса без пропуска трафика через прокси.
