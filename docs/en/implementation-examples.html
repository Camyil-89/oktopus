Deployment

Implementation patterns

Oktopus is an HTTP/HTTPS forward proxy with ACL, client authentication, and access logging. Below are typical patterns for placing the Oktopus server (one node: proxy, API, and control panel) and steering client traffic.

What the server does

Clients (browser, OS, application) send requests to the proxy listen address on the same Oktopus server. The process evaluates rules, may require credentials, records access log events, and opens outbound connections. Administrators open the web panel on that same server (via nginx in the Docker stack)—rules, users, monitoring; the server is usually not exposed to the internet.

For installation steps see Deployment; listen address and mode are in proxy settings.

Recommended: proxy inside the trusted perimeter

The preferred layout keeps the Oktopus server inside the protected perimeter, with no access from the internet. Clients send traffic to its proxy; egress: perimeter → Oktopus → border router (firewall) → internet. The border firewall allows WAN traffic only from that server (or a trusted egress segment), not direct bypass from workstations.

For this pattern, enable MITM in proxy settings: Oktopus issues or uses your organization’s root CA; administrators install that certificate on clients as a trusted root. HTTPS is then decrypted on the proxy—full access log, Lua inspect, and content policy—not just CONNECT metadata.

Recommended

Single controlled exit, ACL, and rich logging; MITM plus org CA for HTTPS visibility and policy; access to the Oktopus server only from trusted segments (VPN, admin VLAN, jump host).

Configuration checklist

  • Network: place the Oktopus server so it is reachable only on the local network; there must be no access from the internet.
  • MITM mode: enable in the panel, generate or upload CA, distribute the root certificate to workstations and servers (GPO, MDM, manual).
  • Clients: system or browser proxy, PAC, or HTTP_PROXY / HTTPS_PROXY pointing at Oktopus.
  • Policy: ACL and proxy auth when needed; with MITM, use inspect rules on the rules page.
  • Monitoring: access log and reports for outbound traffic audit.

Other patterns

Used less often or as a trade-off; new deployments usually only need the recommended layout above.

Oktopus in DMZ reachable from the internet

The server listens on a public or DMZ address; remote users connect to its proxy directly. Works without VPN but increases attack surface: strict ACL, rate limits, current TLS, and isolated protection for the UI are mandatory.

Strict egress on the firewall (optional)

To stop users bypassing the proxy straight to the internet, the border router or firewall often allows WAN traffic only from the Oktopus IP (or a dedicated egress segment); other hosts get deny-to-internet. Clients still need a proxy address or PAC; for HTTPS inspection without browser warnings you need MITM and the org CA installed—otherwise tunnel mode leaves you with CONNECT metadata only.

This does not replace the recommended chain perimeter → Oktopus → firewall → internet; it reinforces it. The server stays inside the perimeter and is still not reachable from outside.

Summary

  • Best fit: one Oktopus server inside the perimeter, egress via the border firewall; MITM mode and CA on clients for HTTPS visibility and policy.
  • Administration — via the UI on the same server, only from trusted networks.
