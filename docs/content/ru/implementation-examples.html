Развёртывание

Примеры реализаций

Oktopus — форвард-прокси HTTP/HTTPS с ACL, аутентификацией клиентов и журналом доступа. Ниже — типовые схемы размещения сервера Oktopus (один узел: прокси, API и панель управления) и направления трафика клиентов.

Роль сервера

Клиенты (браузер, ОС, приложение) отправляют запросы на listen-адрес прокси на том же сервере Oktopus. Процесс проверяет правила, при необходимости требует учётные данные, пишет событие в журнал и устанавливает исходящее соединение к целевому хосту. Администраторы открывают веб-панель на этом же сервере (через nginx в Docker-стеке) — правила, пользователи, мониторинг; с интернета к серверу обычно не ходят.

Подробности запуска — на странице Развёртывание; listen-порт и режим — в настройках прокси.

Рекомендуемая схема: прокси внутри контура

Предпочтительный вариант — сервер Oktopus внутри защищённого контура, без доступа к нему из интернета. Клиенты отправляют трафик на его прокси; egress: контур → Oktopus → внешний роутер (firewall) → интернет. На границе firewall пропускает наружу только трафик от этого сервера (или от доверенного сегмента), а не произвольный обход с рабочих мест.

Для этой схемы обычно включают режим MITM в настройках прокси: прокси выпускает или использует корневой CA организации, администраторы устанавливают этот сертификат на клиенты (доверенные корневые). Тогда HTTPS расшифровывается на прокси — доступны журнал с деталями, инспекция Lua и политики по содержимому запросов, а не только метаданные CONNECT.

Рекомендуется

Единый контролируемый выход, ACL и полный журнал; MITM + CA организации для просмотра и политики HTTPS-трафика; доступ к серверу Oktopus — только из доверенных сегментов (VPN, админ-VLAN, jump-host).

Что настроить

  • Сеть: разместите сервер Oktopus так, чтобы он был доступен только из локальной сети; с интернета к нему доступа быть не должно.
  • Режим MITM: включить в панели, сгенерировать или загрузить CA, раздать корневой сертификат на рабочие места и серверы (GPO, MDM, вручную).
  • Клиенты: системный или браузерный прокси, PAC или HTTP_PROXY / HTTPS_PROXY на адрес Oktopus.
  • Политика: ACL, при необходимости аутентификация прокси; при MITM — вкладка инспекции в правилах.
  • Мониторинг: журнал доступа и отчёты для аудита исходящего трафика.

Другие варианты

Их используют реже или как компромисс; для новых инсталляций обычно достаточно схемы выше.

Прокси в DMZ с доступом из интернета

Сервер слушает на публичном или DMZ-адресе; удалённые пользователи подключаются к его прокси напрямую. Удобно для удалёнки без VPN, но поверхность атаки больше: нужны жёсткий ACL, rate limit, актуальные TLS и отдельная защита доступа к UI.

Жёсткий egress на firewall (дополнение)

Чтобы пользователи не обходили прокси «напрямую в интернет», на внешнем роутере или firewall часто настраивают правило: в WAN уходит только трафик с IP Oktopus (или с выделенного egress-сегмента), остальным хостам — deny на интернет. Клиентам всё равно задают адрес прокси или PAC; для HTTPS-инспекции без предупреждений браузера нужны MITM и установленный CA организации — иначе остаётся режим tunnel с метаданными CONNECT.

Такая схема не заменяет рекомендуемую цепочку «контур → Oktopus → firewall → интернет», а усиливает её: сервер остаётся внутри контура, снаружи к нему по-прежнему не ходят.

Сводка

  • Оптимально: один сервер Oktopus внутри контура, egress через пограничный firewall; режим MITM и CA на клиентах — для просмотра и политики HTTPS-трафика.
  • Администрирование — через UI на том же сервере, только из доверенных сетей.
